# S-009-T4: Enrich trd/SKILL.md — Structured Sections

**Priority:** P1 | **Status:** completed | **Blocked By:** --

## What

Add structured section requirements to `custom-skills/sdlc/trd/SKILL.md` so that TRDs produced by the skill include all sections that `/gstack plan-eng-review` checks for — reducing review round-trips.

## Why

The eng review (plan-eng-review) checks 4 main sections (Architecture, Code Quality, Tests, Performance) plus expects specific outputs (Error Registry, Failure Modes, Coverage Diagram). Our TRD template currently produces documents that miss error handling, observability, security, and coverage goals — causing findings during review that could have been prevented.

## Context

**Eng review checks:**
1. Architecture — system design, data flows (happy/nil/empty/error), state machines, security
2. Code Quality — DRY violations, error handling, technical debt
3. Test Review — 100% coverage goal, coverage diagrams, regression rules
4. Performance — N+1 queries, caching, memory concerns

**Required outputs the review expects:**
- Error/Rescue Registry (maps error → handler → user-visible result)
- Failure Modes list (each with trigger, impact, mitigation)
- Coverage Diagram (visual test coverage map)
- Implementation Task list

**TRD sections per TRD enrichment spec (10 sections):**

| Section | Content | Review Section It Satisfies | When |
|---------|---------|---------------------------|------|
| Architecture Decisions | Each with alternatives + why rejected | Architecture (§1) | Always |
| Error Handling & Failure Modes | Exception table, rescue strategies | Architecture (§1), Error (§2) | Always |
| Security & Threat Model | Attack surface, auth, injection | Security (§3) | When auth/data/APIs |
| Testing Strategy | Coverage goals, test pyramid, diagram | Test Review (§6) | Always |
| Observability Plan | Logging, metrics, alerting, runbooks | Observability (§8) | When runtime exists |
| Rollback Plan | How to undo at each story level | Deployment (§9) | Always |
| Dependencies | What we couple to, what breaks | Architecture (§1) | Always |
| Verification | How we know it's correct beyond tests | Test Review (§6) | Always |
| Performance | N+1 risks, caching, load expectations | Performance (§4) | When data/traffic |
| Long-Term Trajectory | Tech debt, reversibility, path dependency | Long-Term (§10) | When hard to undo |

## How

**Step 1 — Read current trd/SKILL.md:**
- File: `custom-skills/sdlc/trd/SKILL.md`
- Read full content to understand current template/instructions

**Step 2 — Add structured sections guidance:**
- Find the section where the skill describes what a TRD should contain
- Add/replace with the 10-section guidance:

```markdown
## TRD Structure

Every TRD must include these sections. Aligned with what `/gstack plan-eng-review` checks.

### Required Sections (always include)

**1. Architecture Decisions** — Table format:
| Decision | Options Considered | Chosen | Rationale |
Each non-trivial choice must show alternatives and why they were rejected. This is the most-reviewed section.

**2. Error Handling & Failure Modes** — Two parts:
- Exception table: What can go wrong → How it's caught → User-visible result
- Failure modes: Each with trigger condition, impact, and mitigation
This satisfies eng review §1 (Architecture) + the Error/Rescue Registry output.

**3. Testing Strategy** — Include:
- Coverage goals (what percentage, which layers)
- Test pyramid (unit/integration/e2e split)
- Coverage diagram (ASCII or Mermaid showing what's tested)
- Flakiness mitigation (if applicable)
Satisfies eng review §3 (Test Review) + Coverage Diagram output.

**4. Rollback Plan** — Per-story: how to undo if it goes wrong. Include:
- Revert strategy (git revert? feature flag? migration down?)
- Data implications (is state created that can't be un-created?)
- User impact during rollback

**5. Dependencies** — Table format:
| Dependency | Type | Risk | Mitigation |
What we couple to, what breaks if it changes. Include internal and external.

**6. Verification** — How we know it's correct beyond "tests pass":
- Integration checks with real systems
- Smoke test scenarios
- Manual verification steps (if applicable)

### Conditional Sections (include when relevant)

**7. Security & Threat Model** _(when auth/data/external APIs involved)_ — Attack surface, auth boundaries, injection points, PII handling.

**8. Observability Plan** _(when system has runtime behavior)_ — What to log, metrics to emit, alerts to set, runbook pointers.

**9. Performance** _(when data/traffic/latency matters)_ — N+1 query risks, caching strategy, connection pools, expected load, degradation behavior.

**10. Long-Term Trajectory** _(when architecture is hard to undo)_ — Tech debt introduced (acknowledged), reversibility score (1-5 where 5 is easily reversible), path dependency risks.

### Required Outputs (produced during implementation, referenced in TRD)

These are artifacts the eng review expects to find. The TRD drafts them; implementation fills them:
- **Error/Rescue Registry** — maps every known error → handler → user message
- **Failure Modes** — each failure with trigger, impact, mitigation
- **Coverage Diagram** — visual map of test coverage
- **Implementation Task List** — ordered tasks with dependencies
```

**Step 3 — Verify:**
```bash
grep -c "Architecture Decisions\|Error Handling\|Testing Strategy\|Rollback Plan\|Dependencies\|Verification\|Security.*Threat\|Observability\|Performance\|Long-Term" custom-skills/sdlc/trd/SKILL.md
# Should be ≥ 10
```
