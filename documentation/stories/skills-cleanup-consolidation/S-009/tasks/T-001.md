# S-009-T1: Create sdlc/bug Subskill + Update Router

**Priority:** P0 | **Status:** completed | **Blocked By:** S-008-T2

## What

Create `custom-skills/sdlc/bug/SKILL.md` — a mini-workflow subskill for bugs: triage → risk assessment → fix → qa → tracker close. Update the SDLC router (`custom-skills/sdlc/SKILL.md`) to include `bug` as a routable phase.

## Why

Currently, bugs require the full story ceremony (discover → prd → trd → implement) or ad-hoc fixing with no tracking. The sdlc/bug subskill provides a middle ground: a structured mini-workflow that records the bug, assesses risk, fixes it, and closes the loop — all in one invocation of `/sdlc bug`.

## Context

**SDLC router (custom-skills/sdlc/SKILL.md):**
Currently routes to: discover, prd, trd, project-plan, implement, pr-review, retro, decision-doc, memory-review.
The router has a table mapping phases to their SKILL.md paths. Bug needs to be added.

**Entry point by scope (from router):**
```
| Bug or under 30 minutes | Skip to implementation → qa → pr-review |
```
This will change to: `| Bug | /sdlc bug — dedicated mini-workflow |`

**Pre-mortem extraction (from TRD spec):**
The bug skill absorbs these elements from pre-mortem:
- Auto-trigger criteria: db, auth, external, payment
- Risk prompt: "This fix has been deployed. It made things worse. What went wrong?"
- 4 risk angles: Technical, Product, Process, External
- Simplified categorization: `blocks-fix` (must mitigate) or `acceptable` (acknowledged)

**Bug workflow sequence (from TRD):**
1. User invokes `/sdlc bug "description"`
2. Skill calls `brief bug create "description"` → BUG-NNN created
3. Assess severity/risk
4. If non-trivial (touches db, auth, external, payment): run pre-mortem risk assessment
5. Branch if not on feature branch
6. Fix implementation
7. Run qa agent
8. Commit (with approval gate)
9. `brief bug update BUG-NNN status=done`

**depends on S-008-T2** because the skill invokes `brief bug create` which must exist.

- Content:
```markdown

# /sdlc bug — Bug Mini-Workflow

Structured bug handling: record → assess → fix → verify → close. One invocation, full lifecycle.

**Usage**: `/sdlc bug "description of the bug"`

## Phase 1: Record

Create the bug in the tracker:
\```bash
brief bug create "<description>" --body="<details if provided>"
\```

Note the returned BUG-NNN ID. This is your tracking reference for the rest of the workflow.

## Phase 2: Triage

Assess the bug:
- **Severity**: critical (system down) | major (feature broken) | minor (cosmetic/edge case)
- **Priority**: P1 (fix now) | P2 (fix this sprint) | P3 (backlog)
- **Blast radius**: What else could this affect?

Update the bug record:
\```bash
brief bug update BUG-NNN severity=<level> priority=<level>
\```

## Phase 3: Risk Assessment (conditional)

**Auto-trigger** when the bug fix touches ANY of:
- Database migrations or schema changes
- Authentication or authorization logic
- External dependencies (third-party APIs, webhooks)
- Payment or billing flows

**If triggered**, run this assessment:

> Imagine this fix has been deployed. It made things worse. What went wrong?

Evaluate from 4 angles:
1. **Technical**: What could this fix break? Race conditions? Edge cases?
2. **Product**: Could the fix have unintended UX consequences?
3. **Process**: Is there a simpler/safer approach we're not considering?
4. **External**: Anything outside our control (third-party behavior, timing)?

Categorize each risk:
- `blocks-fix` — Must be mitigated before committing. State the specific mitigation.
- `acceptable` — Acknowledged risk, acceptable for this fix. No action needed.

If ANY risk is `blocks-fix`: address the mitigation before proceeding to Phase 4.

**If NOT triggered** (simple bug, low blast radius): skip directly to Phase 4.

## Phase 4: Fix

1. Check branch: `git branch --show-current`. If on `main`, branch out first.
2. Implement the fix.
3. Keep changes minimal — fix the bug, don't refactor adjacent code.

## Phase 5: Verify

Run the qa agent:
- Typecheck passes
- Lint passes
- Related tests pass
- If the fix touches UI: manual browser verification

## Phase 6: Close

1. **Commit gate** (🔒 — get explicit approval):
   \```
   type(scope): subject

   Task: BUG-NNN
   \```
2. Update tracker:
   \```bash
   brief bug update BUG-NNN status=done
   \```
3. If the bug revealed a systemic issue: create a TODO for the underlying problem
   \```bash
   brief todo create "Address root cause of BUG-NNN" --body="..."
   \```

## Escalation

If during investigation the bug turns out to be a feature gap (not a defect):
1. Update bug: `brief bug update BUG-NNN status=escalated`
2. Create a story: `brief story create "..." `
3. Link: `brief bug update BUG-NNN escalated_to=S-NNN`
4. Exit this workflow — the story follows the full SDLC lifecycle.

## Rules

- Always record first (Phase 1), even if the fix is obvious
- Never skip risk assessment when auto-trigger criteria match
- One bug = one commit. Don't bundle unrelated fixes.
- The commit gate (🔒) applies — get approval before committing.
```
