# S-009-T3: Enrich prd/SKILL.md — Structured Sections

**Priority:** P1 | **Status:** completed | **Blocked By:** --

## What

Add structured section requirements to `custom-skills/sdlc/prd/SKILL.md` so that PRDs produced by the skill include all sections that `/gstack plan-ceo-review` checks for — reducing review round-trips.

## Why

The CEO review (plan-ceo-review) checks 11 sections. Our PRD template currently produces documents that miss several of these, causing findings during review that could have been prevented. By including the right sections in the PRD template itself, PRDs pass review on the first attempt.

## Context

**CEO review checks 11 sections:** Architecture, Error & Rescue, Security & Threat, Data Flow, Code Quality, Test Review, Performance, Observability, Deployment & Rollout, Long-Term Trajectory, Design & UX.

**Of these, the PRD owns (requirements-level):**
- Observability → covered by "Success Metrics" section
- Performance → "Performance Requirements"
- Deployment & Rollout → "Deployment & Rollout Strategy"
- Design & UX → "User Experience"
- Security & Threat → covered in "Risk Table"
- Long-Term Trajectory → covered in "Risk Table" + scope modes

**PRD sections per TRD enrichment spec (9 sections):**

| Section | Content | When to include |
|---------|---------|-----------------|
| Exec Summary | 2-3 sentences, stakeholder-readable | Always |
| Problem | Who has it, what they do today, what breaks | Always |
| Success Metrics | Measurable outcomes with targets + how measured | Always |
| Risk Table | Likelihood × Impact × Mitigation | Always |
| Scope Modes | In-scope (must/should/nice), out-of-scope with rationale | Always |
| User Experience | User flows, interaction states, accessibility requirements | When UI/UX exists |
| Performance Requirements | Latency targets, resource limits, degradation thresholds | When measurable perf matters |
| Deployment & Rollout | Phasing, feature flags, rollback criteria, migration path | When rollout has risk |
| Stakeholder Impact | Who's affected, how, when | When >1 team or user type |

## How

**Step 1 — Read current prd/SKILL.md:**
- File: `custom-skills/sdlc/prd/SKILL.md`
- Read full content to understand current template/instructions

**Step 2 — Add structured sections guidance:**
- Find the section where the skill describes what a PRD should contain (likely a template or "sections" area)
- Add/replace with the 9-section table and guidance:

```markdown
## PRD Structure

Every PRD must include these sections. Sections marked "conditional" can be omitted with a one-line justification.

### Required Sections (always include)

**1. Executive Summary** — 2-3 sentences. A stakeholder who reads ONLY this should understand what we're building and why.

**2. Problem** — Three parts:
- Who has the problem (specific user type, not "users")
- What they do today (current workaround or pain)
- What breaks or is missing (the gap)

**3. Success Metrics** — Table format:
| Metric | Current | Target | How Measured |
Each metric must be measurable. "Better" is not a metric. "P95 latency < 200ms" is.

**4. Risk Table** — Table format:
| Risk | Likelihood | Impact | Mitigation |
Include technical, product, security, and process risks. This satisfies the CEO review's Security & Long-Term checks.

**5. Scope Modes** — Three tiers:
- **Must-have** (blocks launch)
- **Should-have** (degrades experience without)
- **Nice-to-have** (defer to follow-up)
- **Out of scope** (explicitly excluded, with rationale)

### Conditional Sections (include when relevant)

**6. User Experience** _(when UI/UX exists)_ — User flows, interaction states (loading, empty, error, success), accessibility requirements. Satisfies CEO review §11 (Design & UX).

**7. Performance Requirements** _(when measurable perf matters)_ — Latency targets, resource limits, degradation thresholds, load expectations. Satisfies CEO review §7.

**8. Deployment & Rollout** _(when rollout has risk)_ — Phasing plan, feature flags, rollback criteria, migration path for existing users. Satisfies CEO review §9.

**9. Stakeholder Impact** _(when >1 team or user type)_ — Who's affected, what changes for them, communication plan.

### What the PRD does NOT cover (TRD owns these)
Architecture, error handling strategy, data flow details, code quality patterns, test strategy. The PRD states *what* must work; the TRD states *how*.
```

**Step 3 — Verify:**
```bash
grep -c "Executive Summary\|Success Metrics\|Risk Table\|Scope Modes\|User Experience\|Performance Requirements\|Deployment" custom-skills/sdlc/prd/SKILL.md
# Should be ≥ 7
```
