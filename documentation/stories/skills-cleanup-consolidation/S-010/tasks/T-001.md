# S-010-T1: Create templates/rules/ with Manifest + Skeleton Files

**Priority:** P0 | **Status:** pending | **Blocked By:** --

## What

Create the `brief/templates/rules/` directory containing `manifest.json` (catalog metadata) and 6 skeleton rule template files. Each skeleton has frontmatter + section headers + one commented example per section (~20-30 lines).

## Why

These templates are what `brief init` copies into `.claude/rules/` (T2). They provide a starting point for project-specific rules — section headers guide what to fill in, commented examples show the format. Without templates, users must create rules from scratch with no guidance.

## Context

**Template format (from TRD, Design Decision D6 — skeleton with section headers + examples):**
```markdown
---
description: <one-line purpose>
paths: [<glob patterns if conditional>]
---

## <Section 1 Name>
<!-- Example: Prefer composition over inheritance for shared behavior -->

## <Section 2 Name>
<!-- Example: All API responses use { data, error, meta } envelope -->
```

**7 templates to create (from TRD manifest.json spec):**

1. `backend-standards.md` — Framework-specific backend architecture (layers, modules, API design)
2. `frontend-standards.md` — Component architecture, ownership ladder, data-fetching boundaries
3. `coding-style.md` — Project-specific conventions (self-improving via retros)
4. `deployment.md` — Deploy commands, env vars, CI/CD, infrastructure
5. `observability-wiring.md` — Provider-specific instrumentation (Sentry, PostHog, OTel)
6. `git-workflow.md` — Project-specific branch naming, PR conventions (extends global rule)
7. `product-analytics.md` — Event taxonomy, naming conventions, tracked outcomes

**manifest.json (from TRD):** Catalog metadata. Note: `detect` field exists in manifest for future `/brief setup` use, but init does NOT parse it (D9 — init copies all, no detection).

## How

**Step 1 — Create directory:**
```bash
mkdir -p ~/.agents/brief/templates/rules
```

**Step 2 — Create manifest.json:**
- File: `brief/templates/rules/manifest.json`
```json
{
  "version": "1.0",
  "templates": [
    {
      "id": "backend-standards",
      "name": "Backend Standards",
      "description": "Framework-specific backend architecture rules (layers, modules, API design)",
      "detect": ["package.json:express|fastify|hono|koa", "Cargo.toml", "go.mod"],
      "paths": ["**/server/**", "**/api/**", "**/routes/**"],
      "file": "backend-standards.md"
    },
    {
      "id": "frontend-standards",
      "name": "Frontend Standards",
      "description": "Component architecture, ownership ladder, data-fetching boundaries",
      "detect": ["package.json:react|vue|svelte|solid"],

    {
      "id": "coding-style",
```

**Step 3 — Create skeleton files:**

`brief/templates/rules/backend-standards.md`:
```markdown
---
description: Backend architecture rules — layers, modules, API design, error handling patterns.
paths:
  - "**/server/**"
  - "**/api/**"
  - "**/routes/**"
---

## Architecture Layers
<!-- Example: Controller → Service → Repository. No cross-layer imports. -->

## API Design
<!-- Example: All endpoints return { data, error, meta } envelope. -->

## Error Handling
<!-- Example: Services throw typed errors; controllers map to HTTP status codes. -->

## Database Access
<!-- Example: All queries go through repository layer. No raw SQL in services. -->
```

`brief/templates/rules/frontend-standards.md`:
```markdown
---
description: Component architecture, state management, data-fetching boundaries.
paths:
  - "**/components/**"
  - "**/pages/**"
  - "**/hooks/**"
---

## Component Architecture
<!-- Example: Smart/dumb split. Pages fetch data; components receive props. -->

## State Management
<!-- Example: Server state in React Query. UI state in Zustand. No mixing. -->

## Data Fetching
<!-- Example: All API calls through hooks in hooks/api/. No fetch in components. -->

## Styling
<!-- Example: Tailwind only. No inline styles. No CSS modules. -->
```

`brief/templates/rules/coding-style.md`:
```markdown
---
description: Project-specific coding conventions. Refined by retro findings.
---

## Naming
<!-- Example: Boolean variables prefixed with is/has/should. -->

## Patterns
<!-- Example: Prefer early return over nested conditionals. -->

## Imports
<!-- Example: Group: stdlib → external → internal → relative. -->

## Testing
<!-- Example: Test files colocated. Name: <module>.test.ts. -->
```

`brief/templates/rules/deployment.md`:
```markdown
---
description: Deploy commands, environment variables, CI/CD pipeline, infrastructure.
---

## Deploy Commands
<!-- Example: pnpm run deploy:production (runs wrangler deploy) -->

## Environment Variables
<!-- Example: DATABASE_URL, SENTRY_DSN — set in .dev.vars locally, CF dashboard for prod -->

## CI/CD
<!-- Example: GitHub Actions: lint → test → deploy on push to main -->

## Infrastructure
<!-- Example: Cloudflare Workers + D1 + R2. Region: auto. -->
```

`brief/templates/rules/observability-wiring.md`:
```markdown
---
description: Provider-specific instrumentation — Sentry, PostHog, OTel, or similar.
---

## Error Reporting
<!-- Example: Sentry.init() in entry point. captureException() for unexpected errors only. -->

## Analytics
<!-- Example: PostHog.capture() for business events. Never for debug logging. -->

## Tracing
<!-- Example: OTel spans wrap external calls. Propagate trace-id in headers. -->

## Alerts
<!-- Example: Sentry alert on new issue. PagerDuty for P1 (>5% error rate). -->
```

`brief/templates/rules/git-workflow.md`:
```markdown
---
description: Project-specific git conventions — extends the global git-workflow rule.
---

## Branch Naming
<!-- Example: feature/JIRA-123-short-desc, fix/JIRA-456-bug-title -->

## PR Conventions
<!-- Example: Squash merge only. Title matches commit convention. Link ticket. -->

## CI Checks
<!-- Example: Required: lint, typecheck, test. Optional: preview deploy. -->

## Release Process
<!-- Example: Tag from main. Changelog auto-generated from PR titles. -->
```

`brief/templates/rules/product-analytics.md`:
```markdown
---
description: Product analytics — event taxonomy, naming, tracked outcomes.
---

## Event Taxonomy
<!-- Example: noun.verb format — user.signed_up, document.exported, subscription.upgraded -->

## Naming Conventions
<!-- Example: snake_case events. Properties: noun_qualifier (e.g. plan_tier, export_format) -->

## Tracked Outcomes
<!-- Example: activation = first document created within 24h of signup -->

## Tooling
<!-- Example: PostHog for events + feature flags. Segment for routing. -->
```

**Step 4 — Verify:**
```bash

# Should print: 7 templates
```
