# S-015-T7: Wrap All 12 writeTracker Callsites in withLock

**Priority:** P0 | **Status:** pending | **Blocked By:** S-015-T6

## What

Wrap every `writeTracker()` call in `lib/commands/story.mjs` (6 sites) and `lib/commands/item.mjs` (3 sites) inside `withLock()` to prevent tracker.yaml races. Also wrap the 3 read-modify-write cycles in `tracker.mjs` (`createItem`, `updateItem`).

## Why

Eng review D2 found that only 3 of the original 12 callsites were planned for locking — all 12 need it. Any `readTracker → modify → writeTracker` cycle without a lock can lose writes when two processes run concurrently. The lock scope must cover the full read-modify-write, not just the write.

## Context

After T6, `nextId()` already acquires the lock for ID allocation. But many callsites do additional work after `nextId` returns — they modify the items array and call `writeTracker`. If two processes interleave between `nextId` returning and `writeTracker` being called, one process overwrites the other's changes.

**The pattern**: wrap the entire `readTracker → [modify] → writeTracker` cycle in `withLock(gitDir, () => { ... })`. For callsites that also call `nextId`, the lock must encompass both — but since `nextId` now acquires its own lock internally (T6), we need to either:
- Have `nextId` accept an option to skip locking when the caller already holds the lock, OR
- Extract the allocation logic so callers can use `allocateId` directly inside their own lock

The cleaner approach: export an `allocateIdUnlocked(projectRoot, gitDir, type)` variant (or just use `allocateId` directly since the caller holds the lock), and have callers that do `readTracker + nextId + writeTracker` acquire the lock themselves and call `allocateId` directly instead of `nextId`.

**All writeTracker callsites (12 total):**

`lib/commands/story.mjs`:
1. Line 285: `storyTaskCreate` — first task sets `current_task`
2. Line 363: `storyTaskUpdate` — task becomes `in_progress`, updates `current_task`
3. Line 374: `storyTaskUpdate` — task becomes `completed`, clears `current_task`
4. Line 478: `storyCreate` — adds new story to tracker
5. Line 513: `storyUpdate` — updates story fields

`lib/commands/item.mjs`:
6. Line 282: `itemCreate` — adds new item to tracker
7. Line 335: `itemUpdate` — updates item fields

`lib/tracker.mjs`:
8. Line 149: `createItem` — adds new item (used by some internal paths)
9. Line 162: `updateItem` — updates item fields

**Note**: Lines 285, 363, 374 are all in story task operations — they read tracker, find the story, modify it, write back. Lines 478, 513 are in story CRUD. Lines 282, 335 are in item CRUD.

For **non-git projects**, `gitCommonDir` returns null, so the lock is skipped — `withLock` should handle this gracefully, or callers should check.

## How

**Step 1 — Add a `withLockIfGit(projectRoot, fn)` helper:**
- File: `lib/tracker.mjs`
```javascript
export function withLockIfGit(projectRoot, fn) {
  const gitDir = gitCommonDir(projectRoot);
  if (gitDir) return withLock(gitDir, fn);
  return fn();
}
```
This is the convenience wrapper that callers use. Non-git projects skip locking.

**Step 2 — Update `nextId` to accept optional `_skipLock` flag:**
- File: `lib/tracker.mjs`
- When callers already hold the lock, they pass `_skipLock: true` to avoid deadlock:
```javascript
export function nextId(items, type, projectRoot, { _skipLock = false } = {}) {
  const cfg = TYPE_CONFIG[type];
  if (!cfg) throw new Error(`Unknown type: ${type}`);

  if (projectRoot && !_skipLock) {
    const gitDir = gitCommonDir(projectRoot);
    if (gitDir) {
      return withLock(gitDir, () => allocateId(projectRoot, gitDir, type));
    }
  }
  if (projectRoot) {
    const gitDir = gitCommonDir(projectRoot);
    if (gitDir) {
      return allocateId(projectRoot, gitDir, type);
    }
  }

  // ... fallback logic unchanged
}
```

- For `storyTaskCreate` (line 280-285): wrap the read-modify-write in `withLockIfGit`
- For `storyTaskUpdate` (lines 358-375): wrap both status-update paths in `withLockIfGit`
